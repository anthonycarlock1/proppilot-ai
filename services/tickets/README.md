# Durable maintenance tickets

The ticket API stores reviewed maintenance assessments and ticket lifecycle records in the project-owned DynamoDB table `anthony-proppilot-tickets` in `us-east-1`. There is no in-memory storage fallback. Local runtime uses inherited AWS profiles; future EKS workloads should use scoped workload identity.

## Two separate actions

1. After a successful model assessment, the agent saves an immutable **draft**, using an internal token. Draft persistence failure leaves the real assessment available but disables ticket creation for it.
2. The user chooses **Review & create ticket**, enters a property/unit, checks the review confirmation, and explicitly submits. Only then is a maintenance ticket created.

The browser cannot supply or change the ticket's model labels, versions, priority policy, or description during confirmation. The ticket service reads that snapshot from the trusted draft. The draft endpoint requires a shared internal token, generated by the local launcher and held in process memory; it is not sent to the browser or stored in an image. The LLM does not create tickets autonomously.

## Run the local cloud-integrated demo

After provisioning storage, install the API/ML environment and agent environment from the project root:

```bash
python3.11 -m venv .venv
.venv/bin/python -m pip install -r services/category/requirements.txt httpx==0.28.1
python3.11 -m venv .venv-agent
.venv-agent/bin/python -m pip install -r services/agent/requirements.lock.txt
```

Then run:

```bash
python3.11 scripts/run_cloud_services.py
```

This starts category (8003), urgency (8005), tickets (8006), and agent (8000) APIs on localhost. Stop older copies of these project-owned demo processes first; the launcher shuts down its children if a service exits. It does not stop unrelated processes or create cloud resources. Ctrl+C shuts down the owned processes. Restarting rotates the internal token and leaves DynamoDB data intact.

In another terminal:

```bash
docker compose up -d --build frontend
```

Open http://127.0.0.1:8080. Assess an issue, review/confirm its ticket, then open **Tickets**. Saved tickets survive refresh and service restarts. Request/chat activity still lives only in browser memory.

This is a shared, unauthenticated development workspace for fictional property data. Authentication and tenant isolation are not implemented. It is bound to localhost and must not be exposed publicly with real tenant data.

## API

| Method/path | Behavior |
| --- | --- |
| `GET /health` | Process liveness, no AWS request |
| `GET /ready` | Describe the configured DynamoDB table |
| `POST /assessments` | Internal token-protected draft write; expires after 24 hours |
| `POST /tickets` | Requires draft ID, property/unit, `confirm_reviewed: true`, and UUID `Idempotency-Key` header |
| `GET /tickets` | Strongly consistent paginated Query, newest IDs first; `limit` 1–50, optional cursor |
| `GET /tickets/{id}` | Read one saved ticket |
| `PATCH /tickets/{id}` | Explicit status and expected version |

The agent exposes matching `/tickets` routes as the frontend backend. It does not proxy the internal assessment-write route.

Example confirmation body:

```json
{"assessment_id":"<draft-uuid>","property_label":"Demo House","unit":"2B","confirm_reviewed":true}
```

Review confirmation must be the boolean `true`; strings and numbers are rejected. It records the caller's review affirmation, not a verified professional inspection. The original model's `manual_review_required` flag remains in the stored assessment.

## Duplicate and concurrency protection

Ticket creation uses one DynamoDB transaction containing the ticket, a durable idempotency mapping, a unique assessment-to-ticket mapping, and a condition that the assessment has not expired. The ticket ID and timestamp are created once per successful transaction.

- Same key and same normalized payload returns the saved ticket (`200`, `replayed: true`), including its current status.
- Same key with different details returns `409`.
- Another key for an already-ticketed assessment returns `409`.
- Transaction contention without a committed result returns a retryable `503`; keep the same confirmation key.
- Missing/expired drafts return `404`/`410`. Draft TTL deletion is asynchronous, so application checks enforce expiration.

The UI retains the idempotency key and submitted details after an uncertain result. Submitted fields are locked for safe retry. Canceling does not delete a saved record; refresh the ticket list if uncertain. There is no arbitrary automatic retry of ticket writes.

Statuses progress `open → in_progress → resolved`. Updates require the expected version and use a DynamoDB conditional update, so stale writes return `409`. Same-status requests with a matching version are no-ops. There is no deletion/reopen API in this increment.

## Storage and lifecycle

`terraform/tickets/` owns only this table, with pay-per-request billing, encryption, point-in-time recovery, and deletion protection. Review `terraform plan` before apply. Local state is ignored; migrate to protected remote state before infrastructure CI.

The table uses `pk`/`sk`: ticket rows share `WORKSPACE#demo` with chronologically sortable UTC IDs; draft, idempotency, and assessment-uniqueness records use separate keys. Drafts alone have an expiration/TTL field. Tickets and duplicate-protection records are retained indefinitely. Listing uses Query with strong consistency and cursors, not a table Scan. Dashboard active counts cover loaded ticket pages, not an unbounded table-wide total.

Do not run an unreviewed destroy or disable deletion protection for convenience. Preserve ticket data/evidence and explicitly plan cleanup when the project is retired. Earlier model/cluster resources are outside this state.

## Verification

```bash
.venv/bin/python -m unittest discover -s tests -p 'test_tickets.py' -v
python3.11 scripts/verify_chat.py
.venv/bin/python scripts/verify_tickets.py
```

The first command uses injected clients, with no cloud writes. The next two use real AWS: assessment draft persistence, three concurrent confirmations producing one ticket, mismatched-key rejection, stale-version rejection, lifecycle updates, and a fresh storage read. The clearly fictional API verification ticket remains saved as resolved. See `docs/ticket-verification.json`.

Frontend tests separately intercept HTTP for UI checks. The opt-in live Chrome test creates a second fictional QA ticket, reloads it, starts work, resolves it, and checks persistence; see `docs/frontend-verification.json`. These are historical evidence, not live health status.

## Code map

- `schemas.py`: validated confirmation and assessment contracts.
- `store.py`: DynamoDB transaction, idempotency, Query pagination, versioned status updates.
- `app.py`: routes, protected handoff, and sanitized errors.
- `services/agent/tickets.py`: frontend proxy and trusted assessment-to-draft mapping.
- `frontend/src/Tickets.tsx`: explicit review form and persisted ticket panel.

The Dockerfile builds a non-root slim image. AWS credentials and the internal token are runtime configuration, never image contents. The local demo currently runs this API through the host launcher; full Compose staging and EKS deployment remain later milestones.
